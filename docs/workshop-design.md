# Workshop Design: Copilot Fluent

Status: **draft, pre-Review-Panel**. Produced via a three-agent review chain (Fable plan → Codex adversarial critique with live repo access → Opus reconciliation) before any of this was written, then authored here incorporating every confirmed correction. See `copilot-fluent-private/docs/reconciled-implementation-plan-2026-09-12.md` for the full chain's reconciliation summary and `docs/decisions.md` for the ADR trail.

## 1. The one-line problem

Enterprise Copilot licences are widely deployed and thinly used. Microsoft's own official preparation for AB-730 does include hands-on exercises, but they're ungraded, self-directed, scattered across multiple separate learning paths and modules with no shared thread between them (see §9 for the full breakdown, including a standalone Cowork module this design doc's own earlier draft missed). This workshop's bet: a gated, continuously-scenarioed alternative that you cannot advance through by reading, covering the great majority of the exam's outline (§6, mapped module-by-module in §7) inside one story.

## 2. Audience

Non-technical knowledge workers with an enterprise Microsoft 365 Copilot licence (the paid add-on, not free Copilot Chat). No git, no CLI, no coding-agent assumption — the first workshop in this factory for a non-engineering audience; all four prior workshops (`terminal-velocity`, `borrow-native`, `half-life`, `heartbeat`) assumed agent-literate practitioners driving a coding harness. The learner's interface is the published website plus their own M365 apps.

AB-730's own Role facet lists both **Administrator** and **Business User**. This workshop deliberately serves only the Business User half — tenant administration, licensing, and deployment are out of scope (see §4). This is a partial-coverage decision, recorded here rather than glossed inside an alignment claim.

Hard prerequisite: a licensed enterprise Microsoft 365 Copilot tenant seat with baseline chat and file-grounding access (§11 covers *additional*, admin-configurable features beyond this baseline — scheduling, notebooks, Agent Store approval — which vary by tenant and are not guaranteed by the seat alone).

**Solo-adaptation claim, corrected to be accurate rather than blanket:** exercises that strictly require a second real person (Module 07's meeting) ship a stated solo adaptation (a supplied transcript fixture). Exercises that require *sharing* an artifact (Module 03's prompt share, Module 07's Page share, Module 08's agent share) can be self-shared to a second personal chat/collection or a second test account where the tenant allows one — named honestly in the module table (§7) as a **partial** mitigation, not a full solo adaptation, since a second licensed identity is not the same as working genuinely alone, and it does not resolve an admin-approval block (§11).

## 3. Format

Self-paced, public — same as all four priors. New wrinkle, named explicitly: the published site is the **primary learner surface** (a no-git audience reads modules on the website, not the repo), not a maintainer build journal with the repo as the real front door. Site implementation itself is Phase 4's deliverable (Astro site, deploy workflow), not this design doc's — see the reconciled implementation plan's Phase 4 section.

## 4. Subject vs. method

Per the Gremlin's "Variant: Tech/Language Workshops" discipline (`workshop-gremlin.md`) — subject and method are named separately even though this isn't a tech/language workshop, because the same discipline applies to any workshop where the two aren't identical.

**Subject:** enterprise Microsoft 365 Copilot — Copilot in Word, Excel, PowerPoint, Outlook, and Teams; the Researcher and Analyst agents; in-app no-code agent creation (Agent Store, template-based agents). Explicitly out of scope: the free baseline Copilot Chat as the target experience, Copilot Studio (the pro-code agent builder — re-introduces a technical audience this workshop is explicitly avoiding), and tenant administration/licensing/deployment (the Administrator half of AB-730's audience).

Note on terminology: Microsoft uses "Work IQ" as the name for a real, current three-layer (Data/Memory/Inference) platform underpinning Copilot/Researcher/Analyst/Cowork — GA'd June 2026, with its own Learn documentation, CLI, MCP server, and public APIs, not merely a marketing gloss. That term still appears nowhere in AB-730's actual outline, though — its nearest wording is "context, like your work files, web data, or the app you're using" (outline bullet 1.1.2). This design doc teaches the outline's own language and does not teach "Work IQ" as a named subject; the scoping decision is unchanged from an earlier draft, but the reason is that **the exam doesn't test it by that name**, not that the term itself is dated — product-platform naming is simply more volatile than the exam outline, so this scope-out is re-checkable, not permanent. (`docs/decisions.md` carries a superseding ADR row correcting an earlier scaffold-stage note that listed Work IQ as a taught subject.)

**Method:** a named-scenario-driven, two-tier-gated, self-paced format. Every exercise is set inside Kellerman & Castle (§5), gated by a required-output checklist (Tier 1, §8) plus an AI-graded rubric (Tier 2, §8).

## 5. The shared scenario: Kellerman & Castle

**Kellerman & Castle** is a boutique financial-services / wealth-management advisory firm — every module's exercises are drawn from this one continuing workplace, not generic disconnected fixtures, per the Workshop Gremlin's named-shared-project principle (established by `borrow-native`'s `relay` and `heartbeat`'s `Checkout`).

The name is a deliberate Patrick Swayze film in-joke (Kellerman's resort from *Dirty Dancing*; Johnny Castle). **Human-confirmed decision (2026-09-12, following the Review Panel's Developer Evangelist finding):** the firm and cast read completely straight in every module's exercises, with zero winking during the gated content itself — but the reveal is made deliberately, once, **after the capstone**: a lightweight bonus note (a footer credit, a Module 09 postscript, or a dedicated easter-egg page — the exact form is a Phase 3/4 decision) tells the learner who Kellerman, Castle, and the rest of the cast really are. No Tier-1/Tier-2 gate keys on character identity (Instructional Designer's finding), so this reveal changes nothing pedagogically — it's pure, cost-free delight for a learner who's stayed straight-faced through nine modules of "a firm a client would trust with their money."

Financial services was chosen deliberately, not decoratively: it gives AB-730's responsible-AI/data-protection domain (25-30% of the real exam) genuine stakes, rather than a bolted-on compliance module. This cuts both ways — see the liability guardrails below and the full brand rules in `docs/brand.md` (Phase 3).

**Liability guardrails** (full rules land in `docs/brand.md`, Phase 3; stated here because they constrain every exercise this design doc specifies):

1. Every learner-produced or shipped example artifact carries a visible **simulation-only** marking.
2. **No buy/sell/hold, suitability, tax, or investment-recommendation language** in any fixture, prompt, exercise instruction, or example output.
3. A stated **jurisdiction assumption**: the fictional firm operates in no real regulatory regime; nothing here is calibrated to any.
4. **Distribution warning**: prompt packs are written against fictional data; reusing them against real client data is the learner's own regulated activity, outside this workshop's scope.
5. **No qualified-compliance-review implication**: Dalton is a character, not a compliance function.
6. All fixture data is plainly fictional — no realistic account numbers, no realistic SSNs/identifiers.

## 6. Canonical-curriculum anchor: AB-730

**Microsoft Certified: AI Business Professional (AB-730)** — a real, current, beginner-level, no-code certification. This workshop's module arc maps onto AB-730's own skills-measured outline rather than inventing a teaching sequence from scratch, and this workshop's explicit success criterion is **designed to prepare** the learner to sit AB-730 — not a claim that completing it will make anyone pass (see §10's hedge, which applies here too, not just later). coderturtle will personally sit the exam once module content exists, as this workshop's dogfooding evidence — the same evidentiary role Ardan Labs' certification played for `borrow-native`.

**Exam mechanics, stated only as far as Microsoft publishes them** (verified directly against Microsoft Learn, 2026-09-12):

- Passing score: **700 / 1000**.
- Duration: **45 minutes**.
- Level: **Beginner** — no coding or app development.
- Proctored via Pearson VUE; "may have interactive components."
- **Question count: not published by Microsoft.** Do not state one.
- **Price: not published as a fixed figure.** Microsoft states only "Price based on the country or region in which the exam is proctored." Do not state a number.
- Skills version: **as of July 22, 2026.**

**Standing rule, not a one-time note:** this workshop's own review chain produced two different specific numbers for price and question count in two successive drafting passes, neither supported by the live source. Neither this document nor any learner-facing copy may state a price or question count for this exam, in any form — not even as a "some sources say" hedge. If a future pass is tempted to fill in a specific figure, that temptation is itself the signal to re-fetch the live pages, not to trust an inherited draft.

Sources: [AB-730 study guide](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/ab-730) (page updated 2026-06-22), [Microsoft Certified: AI Business Professional](https://learn.microsoft.com/en-us/credentials/certifications/ai-business-professional/) (page updated 2026-08-07).

**Full skills-measured outline** (3 domains, 7 objective headings, 30 leaf bullets):

**Domain 1 — Understand generative AI fundamentals (25-30%)**
- *1.1 Understand generative AI capabilities across Microsoft 365 experiences*
  - 1.1.1 Understand how Copilot works to keep your organization's information private and secure
  - 1.1.2 Understand how the context, like your work files, web data, or the app you're using, can affect Copilot responses
  - 1.1.3 Understand the difference between a chat experience and an agent experience
  - 1.1.4 Understand the use case for creating your own agent
  - 1.1.5 Understand the differences in features and capabilities of the Copilot experience in various Microsoft 365 apps
- *1.2 Identify responsible AI and data protection practices*
  - 1.2.1 Identify common risks, including fabrications, prompt injection, and over-reliance
  - 1.2.2 Select verification steps appropriate to the task, including citation checks and human review
  - 1.2.3 Recognize and mitigate risks to sensitive data
  - 1.2.4 Understand how data protection restricts prompt results

**Domain 2 — Manage prompts and conversations by using AI (35-40%)**
- *2.1 Create and manage prompts in Microsoft 365 Copilot*
  - 2.1.1 Understand how to create an effective prompt
  - 2.1.2 Select appropriate resources to reference in a prompt
  - 2.1.3 Save a prompt
  - 2.1.4 Schedule a prompt
  - 2.1.5 Share a prompt
- *2.2 Manage conversations in Microsoft 365 Copilot*
  - 2.2.1 Understand how to find previous conversations
  - 2.2.2 Delete a chat
  - 2.2.3 Rename a chat
  - 2.2.4 Add a conversation to a notebook
- *2.3 Create and manage Microsoft 365 Copilot agents*
  - 2.3.1 Understand when to use Agent Store versus creating a new agent
  - 2.3.2 Create an agent by using a template
  - 2.3.3 Configure an agent that has knowledge
  - 2.3.4 Configure agent settings such as instructions, capabilities and suggested prompts
  - 2.3.5 Share an agent with team members

**Domain 3 — Draft and analyze business content by using AI (25-30%)**
- *3.1 Draft business documents and communications*
  - 3.1.1 Create a new document from a prompt
  - 3.1.2 Generate a document from an existing document
  - 3.1.3 Generate a management summary based on a document
  - 3.1.4 Move data and insights between Microsoft 365 apps
- *3.2 Manage meetings and collaboration*
  - 3.2.1 Describe how to use Microsoft 365 Copilot for meetings
  - 3.2.2 Describe how to use Copilot Pages for collaboration
  - 3.2.3 Describe how Copilot uses memory and instructions

## 7. The module arc

**Module-count rationale:** module count tracks **bullet density**, not raw exam-weight percentage. Domain 2 carries 14/30 leaf bullets (47%) against a 35-40% weight and gets three dedicated modules (03, 04, 08); Domain 1 (9 bullets, 25-30% weight) gets two (01, 02); Domain 3 (7 bullets, 25-30% weight) gets three (05, 06, 07), reflecting that its bullets split across genuinely distinct app surfaces (Word/Outlook, Excel/PowerPoint, Teams) that don't compress into fewer modules without losing the per-surface prompt-pack takeaway. Module 09 is a synthesis capstone, introducing no new bullets.

**Coverage-class vocabulary**, its label borrowed from a pattern *named but not yet populated* in `borrow-native`'s `certification-mapping.md` skeleton (that file is explicitly unauthored — a decided vocabulary, zero content rows — so this document is the first to actually apply it, not reusing a validated track record):
- **Directly exercised** — the module's Tier-1 gate requires mechanical evidence of this bullet, under the workshop's designed (non-fallback) path.
- **Touched but not gated** — the module's material covers this bullet; nothing mechanically checks it (Tier-2 rubric may still grade it as a judgment call).
- **Not covered by this arc** — absent (target: zero for this workshop, given its richer public outline).

Non-bullet subject coverage (product breadth this workshop teaches that isn't itself an AB-730 leaf bullet, e.g. the Analyst agent) is recorded in its own column, never inside the coverage-class column — mixing the two there previously made a literal recount of that column find 5 "touched" entries against a claimed 4, which is exactly the miscount this separation exists to prevent.

**Named limit on the classification itself, not just the count:** "directly exercised" is not applied by one crisp, formalized rule — it's a judgment call about whether a bullet's evidence is strong enough, and reasonable people could draw the line differently in a few specific places (e.g. whether Module 08's Agent-Store-vs-new evidence should count as direct for both 2.3.1 and 1.1.4 since it's one artifact, or only one of them; whether Module 03's resource-referencing check needs an appropriateness key, not just a presence check, to count as fully direct for 2.1.2). This document draws that line as consistently as it can and shows its work per row, but the 25/5/0 split is this document's own best-effort classification, not a mechanically-reproducible count independent of judgment — flagged here rather than claimed as more rigorous than it is.

**Mechanical-checkability discipline, applied uniformly below:** every Tier-1 item is designed as a count, an exact-string search, or a closed-set selection compared against a published key — never a judgment of whether free text "matches," "contains," or "correctly" does something, since that's semantic judgment wearing a checklist's clothes. Where an earlier draft of this table used such wording, it's fixed here, not merely disclaimed. Confirmation-only items (a screenshot or a "confirmed saved/shared" note) are marked **[self-attested]** — they establish that the learner wrote a confirmation, not that Copilot performed the action; this is a named limit of Tier 1 (see §8), not something the wording pretends away.

**Liability-guardrail enforcement, made mechanical where it can be — and named honest where it can't.** Every module whose output is genuinely client-facing prose (05, 06, 09) carries an explicit Tier-1 item requiring **zero matches** against `docs/brand.md`'s prohibited-language list (buy/sell/hold, suitability, tax advice, guaranteed returns, and the rest of the list finalized in Phase 3). **Module 08's "Client Prep" agent is scoped to internal prep notes only, never client-facing, per its own scenario description — but its configured instructions and suggested prompts are still checked against the same list**, since an internal-only agent is one client-facing suggested prompt away from drafting recommendation-flavored content and nothing else in that module's gate would catch it. **None of these items is yet executable** — `docs/brand.md` doesn't exist until Phase 3 authors it; tracked as a named Phase 3 dependency, not resolved here.

**This mechanism is deliberately narrow, and its limit is named rather than papered over.** A literal phrase-list search catches obviously-banned tokens; it cannot catch recommendation-flavored prose that never uses one (e.g. "given the recent performance, this position looks well-positioned for continued growth" contains no banned string yet reads as a recommendation). Closing that semantic gap is not a Tier-1 job — it's added explicitly to the **Tier-2 rubric** for Modules 05, 06, and 09 below ("does this read as factual reporting or does it drift into recommendation, even without a banned word") as a named attempt at a backstop. **This is not the same as the gap being closed**: §8 discloses Tier 2 itself as an untested hypothesis with no pinned model or repeatability guarantee, so a semantic check that depends on Tier 2's own unproven reliability is a real attempt, not a solved problem — named as such rather than implied otherwise.

## 8. The two-tier gate

This subject (a closed SaaS product) has no compiler or test-suite equivalent. Two tiers, named honestly:

**Tier 1 — required-output checklist (closest-to-deterministic).** A short list of mechanically-checkable properties of the produced artifact per module: counts, named data points present, stated bounds, before/after diffs. Design rule: *if a checklist item can't be phrased as counting, searching, or comparing, the module's task is scoped wrong, not the checklist* — applied to every row in §7's table (no "citation-check evidence," "curated," "derived from," or "traceable" left unphrased as a concrete check). **Correction: not every Tier-1 item is literally self-administered by the learner alone.** Most are (counts, structural markers, closed-set selections against a key the learner can see). But Modules 01, 02, and 07 compare the learner's artifact against a **grading-only key deliberately withheld from the learner** (published planted-error strings, exact data-point strings, exact action-item strings) — precisely so identifying them is real work, not a copy operation. Those items are still mechanically checkable (deterministic string/count comparison, never a judgment call) but require a grader — human or AI — with access to the withheld key at grading time, not the learner checking their own work unaided. Call every Tier-1 item "mechanically checkable." Within that, a closed-set/self-visible-key item is **learner-checkable** (distinct from the `[self-attested]` table tag, which means something narrower — see below); a hidden-key item is **grader-checked**. Either way, Tier 1 establishes that an artifact with certain properties exists; it cannot establish that Copilot performed a given operation (a screenshot or transcript is provenance-free). That is a named limit of this gate, not a gap to paper over.

**Tier-1 vocabulary at a glance, so these four terms don't blur together:**

| Term | Means | Applied where |
|---|---|---|
| Mechanically checkable | The general property every Tier-1 item has: a count, string match, or closed-set comparison — never free-text judgment | Every Tier-1 item, always |
| Learner-checkable | A mechanically-checkable item the learner can verify themselves, no hidden key | Most Tier-1 items (structural markers, counts, closed-set answers visible to the learner) |
| Grader-checked | A mechanically-checkable item that needs a hidden key only a grader holds | Modules 01, 02, 07's exact-string checks against withheld fixture keys |
| `[self-attested]` (table tag) | Confirms the learner *says* an action happened (saved/shared/created) — no evidence it actually did | Tagged inline in §7 wherever that's the only available check |

**Tier 2 — AI-graded rubric.** The learner submits their produced artifact against a supplied grading prompt (pasted into Copilot itself) and receives pass/fail plus feedback. This is a deliberate, thematically consistent choice — the grader runs inside the product being taught — and an **untested hypothesis**, marked as such. It has a real, unaddressed circularity: the same probabilistic product both produces and grades the work, with no pinned model version, no repeatability guarantee, and no retry/disagreement path.

**Named risk specific to Module 02:** its own exercise deliberately teaches prompt injection, making its artifact the single highest-risk grading input in the workshop (an artifact containing injection examples could attempt to override the grading prompt that reads it). Minimum mitigation, to be implemented at content time: the artifact is pasted inside an explicit delimiter block, the grading prompt instructs the grader to treat delimited content as data, and Module 02's planted-injection strings are quoted rather than reproduced live wherever the design doc or module content itself discusses them. **This is a design intent, not yet a tested control — named as an explicit content-time acceptance criterion:** before Module 02 ships, the grading prompt must be confirmed to survive a stated set of known injection patterns without being overridden, not merely assumed safe because delimiters exist.

**A missed teaching moment, worth building in deliberately:** Module 02 teaches over-reliance on AI output (outline bullet 1.2.1) while this workshop's own Tier-2 grading mechanism is itself an instance of over-reliance (an AI checking AI-produced work). Content-time authoring should make this explicit somewhere in Module 02 or the capstone — turning a design liability into reinforcement of the exam's own lesson, not leaving the parallel unremarked.

**Undefined, named as an open decision for content time:** "paste the artifact" has no stated form for non-text surfaces — spreadsheets, decks, meeting recaps, Pages. A per-surface submission convention (screenshot + transcript, exported text, etc.) is Coachgremlin's decision when real content is authored, not resolved here.
